# Architecture Overview

SafeGate Edge is built as a series of modular, sequential boundaries. This "prototype spine" ensures that execution cannot occur without passing through distinct safety checkpoints.

## The Spine

1. **Gate (The Interceptor)**: The entry point for all agent action requests. It ensures that no action reaches execution without formal verification.
2. **Trace (Canonical Hashing)**: Normalizes incoming JSON action requests into a strict, deterministic canonical format before hashing. This guarantees that semantic equivalents hash identically, while any semantic mutation breaks the hash.
3. **Readiness (Diagnostics & Preflight)**: Verifies the integrity of the local environment (e.g., policy availability, registry status) before attempting to verify any action.
4. **Policy Boundary (Rules Engine)**: Evaluates the risk level of the canonical action against a declarative, versioned policy to determine if human approval is required.
5. **Human Review Contract**: Packages the action request and policy snapshot into a reviewer-friendly packet that can be safely presented to a human.
6. **Approval Packet Generation**: The cryptographic response from an authorized human approver, explicitly binding their identity to the canonical hash of the action request.
7. **Hardware Boundary**: Reserves the capability to cryptographically verify that the approval was generated by a physical hardware token (e.g., YubiKey) rather than a software process.
8. **End-to-End Demo (Orchestrator)**: The automated runner that proves the entire lifecycle by generating, mutating, verifying, and logging a complete trace.

## The Verification Loop

When an action is intercepted, the `verifier` module acts as the core arbiter:
1. Validates the structural schema of the action.
2. Computes the canonical hash.
3. Resolves the active policy.
4. Evaluates the risk level against policy rules.
5. If approval is required, validates the schema and signatures of the provided approval packet.
6. Validates the hardware attestation status of the approval method.
7. Checks if the approval is explicitly `denied`.
8. Emits a final `allowed` or `blocked` decision, alongside the specific `reason`.
9. The `observe` module logs every step of this loop into a tamper-evident chain.
